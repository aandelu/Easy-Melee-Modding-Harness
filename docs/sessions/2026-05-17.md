# Session 2026-05-17 — Auto-L-cancel macro

Second macro built on top of the harness. Self-contained in `auto_lcancel/`.

## TL;DR

- **Shipped:** `auto_lcancel/auto_lcancel.py` — installs a runtime PadRead
  hook (via meta-flush) that L-cancels Fox automatically while he's in any
  aerial-attack state (NAIR/FAIR/BAIR/UAIR/DAIR).
- **Verified:** `auto_lcancel/test_fox_aerials.py` runs 20 sub-trials
  (5 aerials × short/full hop × L off/cycle-7). Result: `[PASS]` — 7 combos
  L-cancelled (ratio ~0.5), 3 N/A (full-hop aerial finishes in air → plain
  landing → no L-cancel possible by game design), **0 airdodges** in all 20.
- **Design:** press L exactly once per 7-frame cycle (1 press / 6 release).
  Counter byte at `0x803FA470`, resets to 0 on any non-aerial frame.
- **L-cancel check function located:** engine code at `0x8008E4A8` does
  `lbz r4, 0x680(r3); cmpw r4, r0; bgt fail` — single point-in-time read of
  the L/R press timer (Char Data + 0x680) against the 7-frame window. `bgt`
  means `timer ≤ 7` succeeds; cycle-7 design keeps timer in 0..6 (1 frame
  of margin).

## Goal at session start

User: "make a frame-1 reaction macro that re-presses L on every frame the
player is in an aerial attack state, so the 7-frame L-cancel window is
always active when they land. Offline first, but use controller writes
so it can later port online without desync."

## Process & failures (in order)

### Round 1: address-sheet research

Searched the address sheet first. Found three candidates for the L/R press
timer in `Char_Data_Offsets.csv`:
- `0x0678` — Frames Since Analog Trigger Was Moved
- `0x067F` — Frames Since Z Button Was Pressed
- `0x0680` — Frames Since L/R Digital Button Was Pressed

And `0x2354` "Landing Lag Divisor (float)" — described in the CSV as the
field set to 2.0 on a successful L-cancel. The PlCo constants matched:
`0xA0C4 = 7` (the 7-frame window), `0xA0C8 = 2.0f` (the speed multiplier).

Assumption going in: L-cancel mechanic is `0x680 ≤ 7` → `0x2354 = 2.0f`.

### Round 2: discovery — controller writes don't propagate

Wrote `discover_lcancel.py` to verify three things via dme:
1. Direct writes to `0x680` — does the engine react?
2. Controller writes to the L bit at `0x804C1FAC` — does the engine see them?
3. Force Fox through jump+nair via action-state forcing — observe `0x2354`.

Results:
- (1) Worked. `0x680 = 50` → next-frame reads of 50, 51, 52, ... (engine
  increments each frame).
- (2) **Failed.** Held L on the controller for 5 game frames; `0x680` stayed
  at 255. **dme writes to `0x804C1FAC` get clobbered by Dolphin's input
  pipeline.** The harness's `set_digital_buttons` docstring warned about
  this; I should have re-read it before assuming.
- (3) **Failed.** Forcing action state to `KneeBend` / `AttackAirN` made Fox
  play the animations but he stayed grounded — no jump physics, no landing,
  no observation. **Action-state forcing animates without applying
  velocity/position.**

Net of round 2: the "Python writes the controller bit" path won't work;
need the PadRead-hook pattern (`candidate_d2.py` is the reference). And
testing the L-cancel mechanic requires real input-driven jumps, not
forced action states.

### Round 3: first PadRead hook — silent failure

Wrote `lcancel_rig.py` — runtime PadRead hook at `0x803775B8` (the JC-shine
hook point) that drives jump (X) + nair (A) + toggles L every other frame.
Installed via the meta-flush primitive.

First run: **Fox stayed in `Wait` forever.** Watch loop only printed the
first frame; thought the hook wasn't firing.

Two bugs found via diagnostic counter:
- **`pkill -x Dolphin` returns 0 but takes seconds to actually die.** A
  stale Dolphin process lingered; `dme.hook()` attached to the dying
  process; every read failed. Fixed with `pkill -9` + poll `pgrep` for
  empty.
- **Runtime PPC patches get wiped by `seed_snapshot`.** I was installing
  the hook before `seed_snapshot()`, which calls `load_savestate(slot=2)`,
  which overwrites MEM1 — wiping the patch. The boot-time meta-flush gecko
  survives because Slippi's codehandler reinstalls codes after savestate
  loads; my runtime patch did not. Fixed by installing AFTER seed_snapshot
  AND not reloading slot 2 between trials.

After both fixes: the rig drove Fox cleanly through jump → nair → land.

### Round 4: empirical mechanic confirmation

Watched `0x2354` ("Landing Lag Divisor") through a clean nair landing.
**It didn't change.** Reading 0.96f on Fox both with and without L-cancel.

But: **landing-state duration WAS halved.** Trial 1 (L off): Fox in
`LandingAirN` (0x46) for 15 frames. Trial 2 (L on, toggle every frame):
7 frames. Exactly the 2x speed-up the PlCo constant promised.

So the address sheet's description of `0x2354` is misleading (or describes
something I never observed); the real L-cancel observable is **landing-
state duration**. Lesson learned: trust empirical measurements over CSV
descriptions for any field whose docstring isn't perfectly precise.

### Round 5: edge-case concern from user — "frame 8 vulnerable"

User pushback: toggling L every frame might cause unintended airdodges
when an aerial finishes mid-air. Walked through the analysis:
- Airdodge fires on rising-edge L in airborne non-attack state
  (`FallAerial` 0x20).
- Toggle every frame = rising-edge L on 50% of frames. If aerial ends in
  air, the very next frame (state 0x20 at PadRead) could see a stale L
  rising edge → airdodge.
- "Every 7 frames" = rising-edge L on only 1 in 7 frames → ~7× lower
  probability of overlapping with the transition.

User: "we aren't dealing with probabilities. Make a macro that works 100%
of the time. Figure out how many frames an L cancel lasts. Then figure out
the perfect frame to restart your L cancel based on that."

### Round 6: disassemble the engine L-cancel check

Wrote `find_lcancel_check.py`: attach dme, read MEM1 (24 MB), capstone-
disassemble, scan code section for load/store instructions referencing
offset `0x680`. First attempt before booting Dolphin returned garbage —
**the .text section isn't mapped until the game is in-game.** After booting
slot 2, scan found multiple hits. The relevant one is at `0x8008E4A8`:

```
0x8008E4BC  lwz   r5, -0x514c(r13)    ; r5 = global pointer (PlCo-related)
0x8008E4C0  lbz   r4, 0x680(r3)       ; r4 = Frames Since L/R Pressed
0x8008E4C4  lwz   r0, 0x18c(r5)       ; r0 = L-cancel window value
0x8008E4C8  cmpw  r4, r0
0x8008E4CC  bgt   0x8008e4e8          ; if timer > window -> FAIL
...
0x8008E4E0  li    r3, 1               ; SUCCESS
0x8008E4E4  blr
```

Key facts:
- Single point-in-time read of `0x680`. No history / no averaging.
- `bgt` = greater-than, so **`timer ≤ window` succeeds**.
- Window value is at `r13 - 0x514c + 0x18c` — by the PlCo 0xA0C4 constant
  (= 7), this is 7. (I couldn't dereference r13 directly to confirm —
  `r5` read 0; r13 layout post-Slippi is non-trivial. But the PlCo value
  is well-known.)

So: max safe timer at landing = 7. Cycle-N with N ≤ 8 always succeeds.
Cycle 7 (1 press / 6 release) keeps timer in `[0..6]` with 1 frame margin.

### Round 7: switch macro to cycle-7

Updated `auto_lcancel.py`:
- Counter byte at `0x803FA470`, increments each aerial frame, wraps at 7.
- Press L when counter == 0.
- Reset counter to 0 on any non-aerial frame so the next aerial entry
  starts on a press.

Updated `lcancel_rig.py` to use cycle-7 logic in trial-2 path, added a
`FULL_HOP_FLAG` (press X during KneeBend → full hop instead of short hop),
and ran 4 trials: `[PASS]` 15f → 7f on both short hop and full hop. But:
nair animation outlasts full-hop airtime, so Fox stays in `0x41` until
landing in both trials — never reached `FallAerial` (0x20). Airdodge edge
case wasn't directly exercised.

### Round 8: comprehensive aerial test

Wrote `test_fox_aerials.py`: 20 sub-trials (5 aerials × 2 hops × L off /
cycle-7). Aerial selection via stick+A injection in the JumpF frame.
Discovered Fox faces **left** in slot 2 (stick +x triggers BAIR 0x43, not
FAIR 0x42).

Per-aerial baseline landing-state durations (vanilla, no L-cancel):
| Aerial | Lag (f) |
| --- | ---: |
| NAIR | 15 |
| BAIR | 20 |
| FAIR | 22 |
| UAIR | 18 |
| DAIR | 18 |

All halve (~0.5 ratio) under cycle-7 L. **No airdodges in any of the
20 trials.** Three full-hop configs (BAIR, UAIR, DAIR) hit plain landing
(0x2A) because their aerial animation completes in mid-air — both L-off
and L-on land plain, with identical behavior. The macro doesn't break
those configs; they're just unreachable by L-cancel mechanics.

This last test was the empirical confirmation that the airdodge concern
the user raised is mitigated by the cycle-7 design.

## Key insights

See `auto_lcancel/LESSONS.md` for the full list. Highlights:

1. **dme writes to `0x804C1FAC` don't propagate** — Dolphin's input
   pipeline overwrites them. PadRead hook is the only path.
2. **Forcing action states doesn't apply physics.** Aerial state without
   airborne flag = stuck animation.
3. **`0x2354` is not the L-cancel observable** — duration is. Trust
   empirics over CSV descriptions.
4. **Runtime patches are wiped by savestate loads.** Install AFTER
   `seed_snapshot`; cycle in-game instead of reloading.
5. **Use `pkill -9` + poll `pgrep`.** SIGTERM Dolphin takes seconds and
   dme.hook() attaches to dying processes.
6. **PadRead-time action state is the previous frame's state.** Implies
   a 1-frame latency in our input decisions.
7. **PadRead fires once per port per frame.** Guard on `r24` (0-indexed
   port).
8. **Heartbeat + hook-fire counter** when debugging silent failures.
   "State never changed" looks the same as "hook never fired".
9. **`r0` is the literal 0 in `lis`/`addi`/load/store base register
   field.** Don't use r0 as a cursor.
10. **The L-cancel check is a single point-in-time `bgt`.** No history,
    no averaging — the value at the exact frame of the check is all that
    matters.
