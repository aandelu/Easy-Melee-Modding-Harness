## Empirical findings

### Fox jumpsquat and aerial shine timing (B.1 → B.3 data)

From B.1's per-frame log (trigger at frame 2617):

```
2617  p1=Wait     p2=Wait      <- trigger
2618  p1=Catch    p2=KneeBend  (jumpsquat frame 1)
2619  p1=Catch    p2=KneeBend  (jumpsquat frame 2)
2620  p1=Catch    p2=KneeBend  (jumpsquat frame 3)
2621  p1=Catch    p2=JumpF     (first airborne frame; jumpsquat ends here)
```

**Universal**: Fox's jumpsquat is exactly **3 frames** of KneeBend (`0x0018`),
then engine transitions to JumpF (`0x0019`) on frame 4. JumpF = `0x0019`
matches the universal action-state table.

### Fox aerial shine state IDs (newly discovered)

From B.2 / B.3 runs:

| State  | Name (inferred)         | Observed in     |
|--------|-------------------------|-----------------|
| 0x016D | Aerial shine startup    | 3 frames after JC-shine input |
| 0x016E | Aerial shine loop       | Continues from 0x016D |
| 0x0170 | Aerial shine end / fall | When shine times out airborne |

Combined with the previously-known Fox ground shine states (0x0168 startup,
0x0169 loop), this gives the full Fox shine state set in NTSC 1.02.

### Canonical JC-shine timing (B.3, the working macro)

From B.3's per-frame log (trigger at frame 2594):

```
2594  p1=Wait    p2=Wait        <- trigger; harness sets dme flag
2595  p1=Catch   p2=KneeBend    counter 0→1, Y press consumed
2596  p1=Catch   p2=KneeBend    counter 1→2
2597  p1=Catch   p2=KneeBend    counter 2→3
2598  p1=Catch   p2=0x016D      counter 3→4, B+down consumed, AERIAL SHINE STARTUP (no JumpF!)
2599  p1=Catch   p2=0x016D      counter 4→5
2600  p1=Catch   p2=0x016D      counter 5→6, terminal
2601  p1=Catch   p2=0x016E      aerial shine loop
2602+ p1=Catch   p2=0x0169      Fox lands during shine → ground shine loop
```

**Key insight**: Pressing B+down on the LAST KneeBend frame (counter==3 in
the gecko's frame numbering) buffers the shine input. The engine then
transitions KneeBend → aerial shine directly, **skipping JumpF entirely**.
This is the textbook JC-shine technique.

B.2 with shine input one frame later (counter==4, MACRO_PLAN's literal spec)
still works but Fox passes through JumpF for 1 frame before aerial shine.
B.3 is preferable.

### Engine timing model

- Gecko fires at HSD_PadRead (hook `0x803775B8`), which runs once per port
  per frame, BEFORE the engine processes that frame's logic.
- Inputs written to `r25`'s PADStatus during the gecko are picked up by the
  displaced original `lhz r0, 0(r25)` and propagate through the engine for
  the current frame.
- Result: input written at gecko fire on frame T is visible in action-state
  transitions at end of frame T (recorded as frame T+1 in
  `record_window`'s sampling cadence).
- Harness writes (e.g., `force_action_state` via dme) happen between
  frames. Subsequent gecko fires see the updated MEM1.

## Architecture pattern that works

All passing geckos (Candidate A, B.1, B.2, B.3) follow this template:

```
# Setup pointers
0  lis   r11, 0x803F
1  ori   r11, r11, 0xB000     ; flag scratch
2  lbz   r10, 0(r11)          ; r10 = flag

3  lis   r12, 0x803F
4  ori   r12, r12, 0xA424     ; counter scratch
5  lbz   r9,  0(r12)          ; r9 = counter

# Port dispatch
6  cmpwi r24, 0
7  bne   PORT1_CHECK
... Marth-port logic (Z press when flag set) ...

PORT1_CHECK:
   cmpwi r24, 1
   bne   END

# Counter state machine on Fox port
   cmpwi r9, 0
   bne   COUNTER_NZ
   ... trigger arm (set counter=1, press Y) ...

COUNTER_NZ:
   cmpwi r9, 3                ; thresholds drive shine timing
   blt   NO_INPUT_INC
   cmpwi r9, 6
   bge   END                  ; terminal
   ... press B+down, increment counter ...

NO_INPUT_INC:
   ... increment counter ...

END:
   (displaced original)       ; gecko_c2_lines appends this
```

Trigger source = dme byte at `0x803FB000`. Harness drives the flag for
each trial; macro state machine handles the multi-frame sequence.

Hook is **`0x803775B8`** (BEFORE the buttons read) with displaced
`lhz r0, 0(r25)` = `0xA0190000`. This is the only hook that lets us
inject buttons; `0x803775C0` would only work for stick injection. See
`project_pad_buttons_hook_offset.md`.

## Candidate D.1 — the unsolved bug

Goal: replace `lbz r10, 0(r11)` flag read with a chain that reads Marth's
action state from Player Data and triggers on `0xD4..0xD6`.

Pointer chain (matches `Harness.player_data_ptr(1)`):
```
lis  r12, 0x8045
ori  r12, r12, 0x3130
lwz  r12, 0(r12)      ; r12 = P1 GObj ptr (= 0x80C7D260 at runtime)
lwz  r12, 0x2C(r12)   ; r12 = P1 PD ptr   (= 0x80C7D2C0 at runtime)
lhz  r0,  0x12(r12)   ; r0 = action state low 16 bits
cmplwi r0, 0xD4 ... cmplwi r0, 0xD6 ... range check
```

### What we proved with diagnostics

1. **Cave bytes are correctly installed.** `diag_cave_dump.py` verified
   every word of the LOGIC array matches what dme reads back from the
   resolved cave at `0x8066B310`. Codehandler places the branch-back
   (b hook+4) immediately after the displaced word, ignoring any
   `gecko_c2_lines` padding.

2. **Hook is correctly patched.** Hook word `0x482F3D58` decodes as
   `b +0x002F3D58` → `0x803775B8 + 0x002F3D58 = 0x8066B310` (the cave).

3. **The pointer chain works.** `candidate_d_probe` writes Marth's
   action-state half-word to scratch on every Fox pad pass. Probe shows
   `0x803FA428 = 0x000E` when Marth in Wait, `0x803FA428 = 0x00D4` when
   forced to Catch. So `lis/ori/lwz/lwz/lhz` returns the right value.

4. **The minimal trigger works.** `candidate_d_min` (probe-style chain +
   `cmpwi r0, 0xD4 + beq` + write 0x42 to counter at `0x803FA424`) fires
   correctly. After force_action_state, counter byte becomes `0x42`.

5. **The minimal direct write works.** `candidate_min_write`
   (cmpwi r24, 1 + bne END + lis/ori/li/stb) writes `0x42` to counter
   on every Fox pad pass. Counter ends as `0x42`.

### What we couldn't explain

Adding **a single `lbz r9, 0(r11)` instruction** at the start of
`candidate_min_write` (to read the counter) causes seeding itself to
fail intermittently:

```
TimeoutError: load_savestate slot 2: P1 entity never became valid after 11 attempts
```

This is `candidate_min_lbz_write` — only difference from `candidate_min_write`
is one extra lbz. The lbz reads from `0x803FA424`, which is the same
address the subsequent stb writes to. No register conflict (RT=9, RA=11).
Encoding `0x896B0000` is correct. The instruction is a normal load.

Even more troubling: in the full D.1 / v2 / v3, the trigger arm at pos
20-21 (which writes counter=1) never executes despite Marth being in
Catch for many frames. Diagnostic sentinels written at intermediate
positions (pos 16, pos 21, with scratch byte at `0x803FA428`) confirm
that execution never reaches pos 16 OR pos 21. Yet the cave bytes are
correct and the branches' offsets check out.

### Hypotheses ruled out

- **Wrong branch offsets.** Manually re-derived all forward offsets and
  verified via cave dump. Correct.
- **Wrong instruction encoding.** Decoded suspect words bit-by-bit
  (cmplwi, blt, bgt, cmpwi r12 0, etc.). Correct.
- **Register clobbering by surrounding code.** r9/r10/r11/r12 are
  ABI-volatile and used freely by working candidates A, B.1, B.2, B.3.
- **Action state at wrong offset.** Verified via Python dme read that
  Marth's action-state byte (0xD4 = Catch) sits at PD `+0x13` (low byte
  of word at PD `+0x10`); `lhz r0, 0x12(r12)` reads the half-word
  `0x00D4`.
- **Pointer-null branches taking unexpectedly.** NOP'd `beq END` at
  pos 11 and pos 14; no change in behavior.
- **Counter check taking spuriously.** NOP'd `cmpwi r9, 0` and
  `bne COUNTER_NZ` at pos 5 and pos 6; no change.
- **Padding word (0x00000000) executed and traps.** Codehandler places
  branch-back immediately after displaced, padding word ends up AFTER
  the branch-back and is never reached.
- **Slippi's codehandler reads only n_lines\*2 words.** Verified yes,
  but it appends its own branch-back at offset `len(LOGIC)+1`, not at
  the end of the padded array.

### Working theory

Something about how Dolphin's JIT recompiles slightly-larger cave
regions, or some interaction between Slippi's codehandler and the
gecko length, makes certain seemingly-equivalent code sequences fail.
The most suspicious clue is `candidate_min_lbz_write` — a single extra
lbz triggers seeding failure consistently, while `candidate_min_write`
works every time.
